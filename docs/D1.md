# d1-omni (reference map for the Swift port)

Verified against `LiquidAI/d1-omni-600M` revision
`02b55d7076f15129e59ab3f94783f32c4b088674` (`modeling_d1.py`, `encoder.py`,
`prompt.py`, `vision.py`, `audio.py`) with torch 2.14.0, torchvision 0.29.1,
and transformers 5.17.0. `model.safetensors` is 2,348,774,500 bytes, SHA-256
`0713bb05270c2685ad106522f4092bceeeb3a93cf79b401f399a712296c911e1`
(`D1Weights.d1Omni600MArtifact`).

## What differs from von

| | von | d1-omni |
|---|---|---|
| Backbone | ModernBERT-large, 28 layers | LFM2.5-Encoder: 10 short-conv + 6 GQA layers, bidirectional |
| Rows per question | 1, plus a null pass for default Noul | 1 |
| Head | MLP at `[MASK]` positions | question-type embedding, 2 pre-norm transformer layers, MLP |
| Calibration | input-conditioned temperature map | fixed temperature per type and option-count bucket (text only) |
| Answers | rounded; confidence = p1 - p2 | unrounded; confidence = max p |
| Media | none | image or audio prefix embeddings, shared trunk |
| Usage | approximate characters / 4 | positions read (prefix + tokens), 0 output |

Both use the same Decision Index question schema, so `SystemOneEngine`,
`QuestionEntry`, and the answer types are shared.

## Prompt (`D1Prompt`)

```
<bos> <|reserved_7|> state <|reserved_8|> instructions
      (<|reserved_9|> <|mask|> option <|reserved_10|>)×k <|reserved_11|>
```

- Caller text has every `<|name|>` rewritten to `<¦name¦>`, so a state cannot
  forge a delimiter or marker. `D1ModelProfile.markerText` is therefore `nil`.
- A text state passes through; ordered fields serialize like
  `json.dumps(state, ensure_ascii=False)`.
- The option block gets `max(96, min(24k + 32, maxLength / 2))` tokens, split
  evenly across options; the state is truncated on the right to fit.
- Options: Choice `key: description` (the key alone when the description is
  `nil` or empty); Score `level i: text`; Noul `[false, true]` with defaults
  "no, the statement does not hold" / "yes, the statement holds".
- Image requests use 896 text positions and plain `false: no` / `true: yes`
  Noul defaults. Audio requests use 15,360, write choices as
  `option_000: description`, and always use the plain Noul.
- Usage counts every position the trunk reads.

`D1Tokenizer` loads `tokenizer.json` with swift-transformers' BPE tokenizer,
mapping transformers 5's `TokenizersBackend` class to `PreTrainedTokenizerFast`.
Ids match Python on the fixture's Unicode, emoji, RTL, code, and long inputs.

## Trunk and head (`D1Trunk`, `D1DecisionHead`)

- Short conv layers: `out(c · conv3(b · u))` from a 3×d input projection, with
  a centred depthwise 3-tap kernel. Inputs are zeroed at padding first.
- Attention layers: GQA (16 query, 8 KV heads), per-head RMSNorm on Q and K,
  non-traditional RoPE with θ = 1e6 over absolute positions.
- SwiGLU feed-forward of width 4,608; RMSNorm everywhere; a final RMSNorm.
- A media prefix attends only to itself and the last prefix position never
  reads the first text position through the convolution, so the prefix is a
  function of the media alone. A request runs it through the trunk once and
  caches what text reads from it: each attention layer's keys and values
  (after RMSNorm and RoPE) and each conv layer's last `b · u`. Every question
  then runs only its text positions, from RoPE position P, against those
  states. The reference re-runs the prefix per question; logits agree with
  that path to 5e-5.
- The head adds a type embedding (choice 0, score 1, noul 2), runs two
  PyTorch `TransformerEncoderLayer`s (pre-norm, ReLU, 16 heads) over text
  positions, and scores markers with LayerNorm → Linear → GELU → Linear.

## Vision (`D1Vision`)

- `layout`: LFM2-VL smart resize (32-pixel factor, 64–256 projected patches per
  crop). Images over twice the budget are cut into up to ten 512-pixel tiles
  plus a thumbnail. The grid search follows CPython's set order, embedded as
  `D1Vision.tileGrids`.
- Crops are resized with ATen's uint8 antialiased bilinear kernel, reproduced
  bit for bit in `AntialiasedResize` (int16 weights, horizontal then vertical
  pass, uint8 intermediates). On arm64 torchvision takes this native path.
- SigLIP2 NaFlex: patch Linear plus a 16×16 position grid resized with the
  float antialiased kernel; 12 pre-norm layers (tanh GELU, LayerNorm ε = 1e-6).
  Each crop runs unpadded, equivalent to the reference's key-padding mask.
- 2×2 pixel unshuffle, then Linear → GELU → Linear into the trunk width: one
  prefix embedding per 32×32 pixels.

## Audio (`D1Audio`)

- Clip cut to 30 s, padded to 0.5 s. Preemphasis 0.97; centred 512-point STFT
  with hop 160 and a symmetric 400-sample Hann window; power spectrum; Slaney
  mel (128 bins, `MelFilterbank`); `log(x + 2^-24)`; per-feature normalization
  over the `n / 160` valid frames.
- 8× ConvSubsampling (3×3 stride-2 conv, then two depthwise-separable stride-2
  stages) with the time mask reapplied before every module.
- 17 FastConformer layers: half-step FFNs, Transformer-XL relative-position
  attention (`rel_shift` implemented as a gather at column `t-1-i+j`), a
  GLU/depthwise-conv module with folded BatchNorm, and an output LayerNorm. The
  conformer runs over valid frames only, equivalent to its masks for one clip.
- Adapter (LayerNorm → Linear → GELU → Linear) and a residual correction:
  one prefix embedding per 80 ms.

## float16 (`precision: .float16`)

The checkpoint and the reference are float32. `D1Precision.float16` is an
opt-in mode for memory-bound devices, matching the model card's GPU path
(`dtype=torch.float16`), which kept every top answer while bfloat16 did not.

- `D1Weights.array(_:)` converts each tensor to float16 on the CPU (vImage,
  round to nearest even) into a page-aligned buffer that Metal wraps without a
  second copy, so loading never holds a float32 copy in MLX.
- A weight float16 would turn into infinity (magnitude 65520 or more), read
  while converting, or a folded BatchNorm scale or shift that large, makes
  `D1Model` throw `WeightsError.float16Overflow` naming it. Values used only
  in float32 (BatchNorm running statistics) are not limited.
- Every constant joins the compute dtype so nothing promotes back to float32:
  the trunk's padding and `keepRight` multipliers and its additive mask, whose
  blocked value is -65504 (`encoder.py` clamps -1e9 to `finfo(float16).min`);
  the head's key mask; image patches; the resampled position grid; audio
  features after the float32 mel front end; conformer time masks and relative
  positions.
- Stays float32: the mel front end (as `audio.py` does), the position-grid
  resampling and BatchNorm folding (computed in float32, then cast), attention
  softmax accumulation in the conformer (`precise: true`), and the head logits,
  which are cast back before calibration.

| Check (GPU, M4 Max) | float16 vs the float32 fixture |
|---|---|
| Top answer, text / image / audio requests | identical on every row |
| Worst probability difference, text / image / audio | 5.8e-3 / 5.1e-3 / 4.7e-3 (image and audio 3.8e-3 / 1.6e-3 when every row re-ran the prefix) |
| Weight memory | 1.12 GB (float32: 2.24 GB) |

## MLX exports (`LiquidAI/d1-omni-600M-MLX-fp16`, `-MLX-8bit`)

LiquidAI publishes float16 and 8-bit exports written by mlx-vlm's converter
(`model_type: d1_omni`). `D1Weights` reads either layout by PyTorch name, so
the model code is shared; a folder with `model.safetensors.index.json` is an
export (`D1WeightLayout.mlx`).

What the converter changes, and how the loader undoes it:

| Export | Loader |
|---|---|
| `vision.tower.vision_model.*` → `vision.tower.*`; `head.scorer.N` → `head.scorer.layers.N`; head `self_attn.out_proj` → `attention.out_proj`; NeMo audio names → Parakeet names (`pre_encode.conv` → `subsampling.layers`, `linear_q` → `q_proj`, `pos_bias_u` → `bias_u`, `batch_norm` → `norm`, ...) | `D1Weights.mlxName` |
| the head's fused `in_proj` split into `attention.{query,key,value}_proj` | stacked back on the output axis; packed rows stack as they are |
| convolutions channels-last (`[D, 3, 1]`, `[out, k, k, in]`, `[out, 1, in]`) | transposed back to PyTorch's layout |
| `num_batches_tracked` dropped; floats cast to float16 | schema follows suit |
| 8-bit: every linear and the token embedding outside the vision tower, except the head's scorer and type embedding, affine-quantized in groups of 64 | `QuantizedLinear` / packed embedding; group size and bits read from the stored shapes and checked against `config.json` |

`D1Weights.mlxSchema(for:floatType:quantization:)` reproduces the published
exports' 1,075 tensor names and the 263 modules the 8-bit export quantizes
(`testdata/d1_omni_600m_mlx_exports_v1.json`, from the Hub's index files).
`testdata/d1_tiny/` is a tiny random d1-omni in the PyTorch layout plus the
float16 and 8-bit exports mlx-vlm 0.7.11 writes from it, with mlx-vlm's logits
(`tools/d1_mlx_export_fixture.py`); the Swift logits match them within 1e-4
(float32) and 1e-2 (float16, 8-bit), on the CPU in CI.

No SHA-256 pin is recorded for the exports yet (the Hub tooling used here
exposes sizes only), so they are checked against the schema rather than byte
for byte; pass `artifact:` to pin one. They are float16: load them with
`precision: .float16` to keep their footprint (1.17 GB and 0.73 GB). The model
card reports 175/175 top answers kept against float32, with maximum probability
differences 0.007 (float16) and 0.060 (8-bit).

## d1-3B (`D1ChatBackend`)

d1-3B (`LiquidAI/d1-3B`) is LFM2.5-VL-3B used as a causal language model. It
has no decision head: the answer is read off the next-token logits at the
answer slot. `D1ChatBackend` ports the reference's `prompt.py` and `api.py` at
their published defaults: no system turn, `json_only` states, `desc` options,
no lead, and no calibration.

- **Prompt:**
  ```
  <|startoftext|><|im_start|>user
  {state}

  QUESTION:
  {question}<|im_end|>
  <|im_start|>assistant
  ```
  - A text state is written as is.
  - Fields are written as `json.dumps(…, indent=2, ensure_ascii=False)`.
- **Questions:**
  - A choice lists `{code} {description or key}` under `Options:`.
  - A noul adds `Yes: …` / `No: …` when it has criteria. A missing side prints
    `None`, as Python does.
  - A score lists `{i} {level}`.
- **Option codes:**
  - Choice options get single-token codes: their own letters when every label
    is one letter, else A–Z, else 00–99.
  - A code that is not one free token falls back to the reference's pool.
- **Readout:**
  - Each option scores its best token form: the code and its spaced variant,
    `yes`/`Yes`/`YES` against `no`/`No`/`NO`, or the score digit.
  - The scores are softmaxed over the options, using output-embedding rows
    gathered from the tied head. Full-vocabulary logits are never formed.
- **Answers:**
  - A noul is P(yes).
  - Choice and score report the best option's probability as confidence.
  - A score is the expected level.
- **Batching:**
  - A lone question is one pass over its whole prompt.
  - Several questions share their state: it is prefilled once (`DecoderCache`)
    and every question continues it. This evaluates the reference's tree
    (`hybrid.py`) as a prefix plus branches.
- **Pictures** (`SystemOneMedia.images`), as `runner.py` and transformers'
  LFM2-VL run them:
  - Each picture over one megapixel is downscaled first with Pillow's bicubic
    filter (`cap_pixels`).
  - The chat template writes `<image>` per picture at the head of the user
    turn, before the state. LFM2-VL's processor expands each into
    `<|image_start|>`, the tile tags and 256 `<image>` tokens per 512-pixel
    tile, `<|img_thumbnail|>` and the thumbnail's tokens, and `<|image_end|>`.
    A picture that is not tiled is one smart-resized view (64–256 tokens).
  - `LFM2VLVision` (`SystemOneDecoders`) encodes the views with the so400m
    SigLIP2 NaFlex tower and the projector. The features replace the `<image>`
    tokens in order.
  - The pictures belong to the prefix, so several questions still share one
    prefilled state. The state's text cannot contain `<image>`: a prompt
    whose image tokens do not match its pictures is rejected.
  - Audio is not supported.

`tools/d1_3b_fixture.py` records:
- the reference's prompt text, codes, token groups and answers on the tiny
  LFM2 trunk, for a multi-question text state, a 28-option fields state that
  needs fallback codes, and an empty state with `{what, examples}` score
  levels;
- token counts from a stand-in tokenizer.

Swift reproduces the prompts, codes and groups exactly. The MLX test matches
the answers within 1e-3; a Python MLX transliteration of the
prefix-and-branches path matches within 5e-7.

`tools/d1_3b_vision_fixture.py` runs the pictures through transformers 5.22.1
(torchvision 0.29.2) and Pillow 13.0.0 on a tiny random LFM2-VL, saved in
transformers' and mlx-vlm's layouts. It records:
- three synthetic pictures: a small one that is upscaled, one over a megapixel
  that is capped and tiled 3 × 2 with a thumbnail, and one that is downscaled;
- their capped bytes' and every processed view's SHA-256, recovered from the
  processor's `pixel_values`, and a summary of the projected features;
- prompt token ids and answers for a two-question state with one picture, a
  lone question with two pictures, and three questions on two pictures.

Swift reproduces every capped picture and view bit for bit, and the prompts
exactly. The MLX tests match the features within 1e-4 and the answers within
1e-3 in both layouts; a Python MLX transliteration of the image path matches
the features within 1e-6.

## d1-2B (`D1SetBackend`)

d1-2B (`LiquidAI/d1-2B`) is an LFM3-VL model read through its tied head under
`set` attention. `D1SetBackend` answers noul, choice and score questions on
text states. It follows mlx-vlm's `d1_lfm3_vl`, which adapts the code LiquidAI
ships with d1 checkpoints.

- **Prompt:** d1-3B's ChatML state and question blocks. Each question ends with
  `<think></think>`, and its last token is the answer slot.
  - Caller text goes through `plain`: each special token's text gets U+200B
    after its first character, so `<|im_end|>` in a state stays text.
  - Past 26 options, the codes follow `d1_codes` (2 on d1-2B: `AA`, `AB`, …).
- **Set rows:** up to `d1_set_size` questions (16 on d1-2B) share one row.
  - The state and the first question are encoded together. Each further
    question follows as `QUESTION:\n{suffix}`.
  - On full-attention layers, the state sees the whole row, every token sees
    the state, and each question sees itself. Sliding and convolution layers
    stay causal.
  - Positions run along the row.
- **Readout:**
  - Each option scores the best of its token forms at its question's slot.
  - Scores are divided by `calibration.json`'s temperature for the question's
    bucket. d1-2B uses 1.3374 for every bucket, and the division is skipped
    when it is 1.
  - The scores are then softmaxed.
- **Answers:**
  - A noul is P(yes).
  - A choice is its first best option.
  - A score is its **median** level: the first level whose cumulative
    probability reaches one half.
  - Confidence is the best option's probability.
  - Score levels must be 2–10 strings, as the reference checks.
- **Pictures** (`SystemOneMedia.images`), as d1-2B's `media.py` and LFM3-VL's
  processor run them:
  - Each picture over `d1_vision_max_pixels` (1,638,400 on d1-2B) is
    downscaled first with Pillow's bicubic filter.
  - The chat template writes `<|vision_start|><|image|><|vision_end|>` per
    picture at the head of the user turn, before the escaped state. The
    processor expands `<|image|>` to one token per 2 × 2 block of 16-pixel
    patches after a smart resize to multiples of 32 pixels.
  - `LFM3VLVision` (`SystemOneDecoders`) encodes each picture once. Its
    features fill the state's `<|image|>` tokens in every set row, which read
    them both ways like the rest of the state.
  - `plain` keeps the image token in caller text from reaching the model.
- **Not supported yet:** audio, video, spoken questions, and the typed
  questions (multiple choice, text/number/date reads, estimates, boxes).

`tools/d1_2b_fixture.py` calls mlx-vlm's own prompt, packing, readout,
calibration and answer code on the tiny LFM3 trunk. Its stand-in tokenizer
splits special tokens out of text, as Hugging Face tokenizers do. The fixture
covers:
- a five-question text state with special tokens in the state and in a
  description, packed two to a row;
- a 30-option fields state with fallback codes;
- an empty state.

Swift reproduces the prefixes, suffixes, token groups and packed rows exactly
(ids, state lengths, question groups, slots). The MLX test matches the answers
within 1e-3. A Python MLX transliteration of the batched path matches to
1e-16.

`tools/d1_2b_vision_fixture.py` adds pictures. It builds a tiny random LFM3-VL
tower and projector on testdata/lfm3_tiny's trunk, saved in transformers' and
mlx-vlm's layouts:
- Preprocessing follows d1-2B's vendored `image_processing_lfm3_vl.py`
  (`smart_resize`, `patchify`, transformers 5.22.1's torchvision resize and
  normalization). Its cap uses Pillow 13.0.0.
- The tower, projector, set packing and answers are mlx-vlm 0.7.11's.
- Three synthetic pictures: one upscaled, one capped (900 × 700 at a
  409,600-pixel budget), and a wide one.
- Three requests: three questions over two rows with one picture and a state
  holding `<|image|>` as text; a lone question with two pictures; and two
  questions on one picture.

Swift reproduces every capped and resized picture bit for bit, and the rows
exactly. The MLX tests match the features within 1e-4 and the answers within
1e-3 in both layouts; a Python MLX transliteration of the tower matches
mlx-vlm exactly.
